## Deferred / larger issues for user

### F5 — HIGH (functional) — ✅ NOW FIXED (commit pending): suggest_writes proposed tool-calls can't be Approved/Rejected from chat
**Fix shipped & verified end-to-end:** added `ai_tool_calls.call_id` (migration `00139`) linking a
record to the assistant message's OpenAI tool_call id; `recordToolCall` stores it (`sse.go` passes
`tc.ID`); `GetConversationMessages` now enriches each message tool_call with its record `status`
and replaces the id with the record UUID (`ToolCall.Status` added, `omitempty` so the model path is
unaffected). No frontend change needed (it already reads `tc.status`/`tc.id` and refetches on
`done`). **Verified:** propose `create_reminder` → **Approve/Reject render** → Approve → record
`status=executed`, `executed_by` set, and the reminder event was created in `project_events`.
go vet/build clean; tool-call tests pass; only the two documented known-flaky tests remain.

_Original root-cause analysis (kept for reference):_
**Repro:** workspace+project autonomy = `suggest_writes` with `create_reminder` enabled → ask
the chat to create a reminder. Backend correctly records the call as **`status=proposed`**
with full `input_json` (verified in `ai_tool_calls`) and the assistant says "pending approval"
— but **no Approve/Reject buttons ever render** (confirmed live during streaming AND after
reload). The proposed write can never be completed or dismissed from the UI; it's stranded.

**Root cause (two coordinated gaps):**
1. `internal/ai/sse.go:341-348` — the proposed `ai_tool_calls` record is created but its UUID
   (`rec.ID`) is discarded (`_ = rec`). The `tool_call` SSE event (`:323`) carries no `status`;
   the `tool_result` event (`:389`) carries `status` but **not** the record UUID. The approve
   endpoint `POST /v1/ai/conversations/{id}/tool-calls/{tcid}/approve` needs that UUID.
2. `web/src/components/AIChatPanel.tsx:560` — the `tool_result` stream handler is
   `{...tc, result: ev.result}`, which **drops `ev.status`**, so the streamed tool call never
   becomes `status:'proposed'` and `ToolCallCard` (`:169`) never shows the buttons.
3. On reload, persisted messages render from `ai_messages.tool_calls` (OpenAI wire format —
   no status, OpenAI call-id not the `ai_tool_calls` UUID), so the buttons are also absent there.

**Recommended fix:** (a) in `sse.go`, include the proposed record UUID in the `tool_result`
event (e.g. `"id": rec.ID`); (b) in the frontend SSE parser + `tool_result` handler, propagate
`status` and carry the record UUID as the approve target (distinct from the OpenAI call-id used
for matching); (c) enrich the conversation-messages API to join `ai_tool_calls` so proposed
calls remain actionable after reload. Deferred (touches the streaming contract end-to-end) — out
of scope for an in-place same-run fix; flagged for your decision.

_Note: `auto_routine`/`full` autonomy (auto-execute) and `read_only` (refuse) paths are
unaffected — only the `suggest_writes` human-approval loop is broken._

### Backend/agent-surface findings (from Phase 5 subagents — non-blocking)
- **ETag conditional GET not implemented**: single-resource GETs set an `ETag` (a timestamp
  value, not a hex hash) but `If-None-Match` is ignored → no 304. ETag is only used for
  `If-Match` optimistic-concurrency writes. Missing optimization, not a correctness bug.
- **List envelope inconsistency**: only `/pages` wraps results in `{items:[…]}`; samples,
  experiments, iterations, risks, artifacts, events, workspaces return **bare arrays**.
- **PAT scopes not enumerated in OpenAPI**: accepts `read:<res>`/`write:<res>` strings but the
  spec types `scopes` as plain string (no enum) — hard to discover without reading source.
- No project `DELETE` endpoint (archive only) — by design.
